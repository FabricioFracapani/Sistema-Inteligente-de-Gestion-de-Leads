1. MEDIDAS DE SEGURIDAD IMPLEMENTADAS (13 controles)
------------------------------------------------------------
  [CSP  ] Content-Security-Policy             — Restringe fuentes de scripts, estilos e imágenes
  [HSTS ] Strict-Transport-Security           — Fuerza HTTPS (activado solo en producción)
  [XFO  ] X-Frame-Options: DENY               — Previene clickjacking
  [CTO  ] X-Content-Type-Options: nosniff     — Evita MIME-type sniffing
  [RP   ] Referrer-Policy                     — Controla información de referrer en navegación
  [PP   ] Permissions-Policy                  — Deshabilita APIs innecesarias del navegador
  [COOP ] Cross-Origin-Opener-Policy          — Aísla el contexto de navegación
  [CORS ] Cross-Origin Resource Sharing       — Restringe acceso a orígenes autorizados
  [RL   ] Rate Limiting                       — 60 req/min por IP en /api/leads
  [CSRF ] CSRF Token                          — Token por sesión + SameSite=Strict
  [SAN  ] Input Sanitization                  — Strip HTML, caracteres de control, límites de longitud
  [VAL  ] Validación server-side              — Email RFC 5322, nombre >= 2 chars, teléfono >= 7 dígitos
  [HON  ] Honeypot anti-spam                  — Campo oculto _hp_field para detectar bots

2. CAPA DE DATOS — ROW LEVEL SECURITY (Supabase PostgreSQL)
------------------------------------------------------------
  Roles definidos: anon, authenticated, service_role
  Políticas RLS: 11 políticas en 4 tablas

  Tabla leads:
    - anon: solo INSERT (formulario landing page)
    - authenticated: SELECT + UPDATE (dashboard y ventas)
    - service_role: bypass total (pipeline n8n)

  Tabla lead_events:
    - authenticated: SELECT (consulta de trazabilidad)
    - append-only: sin políticas UPDATE ni DELETE

  Hashing de PII:
    - SHA-256 de email y teléfono para búsqueda interna
    - ATENCIÓN: SHA-256 sin salt NO constituye anonimización
      criptográfica. Funciona como campo auxiliar de búsqueda.
    - Los datos originales (email, teléfono) se conservan en la tabla
      para el funcionamiento del sistema (envío de emails).
    - IP anonimizada mediante máscara /16 (IPv4) o /48 (IPv6)

5. RIESGOS ESPECIFICOS DE LLM (OWASP Top 10 for LLM Applications v1.1) — M-03
------------------------------------------------------------
  El pipeline invoca un LLM (GPT-4o-mini) dos veces por lead: para
  clasificar la intencion y para generar el email de respuesta. Esto
  introduce una superficie de riesgo que las 13 medidas de la seccion 1
  (pensadas para la capa web) no cubren. Se analiza contra el catalogo
  OWASP Top 10 for LLM Applications:

  [LLM01] Prompt Injection
    Riesgo: el mensaje del lead es texto libre de un tercero no confiable
    que se concatena al prompt ("... + $json.mensaje"). Un atacante podria
    intentar que el LLM ignore sus instrucciones de sistema (p. ej. forzar
    una clasificacion o prioridad falsa, o hacer que el email generado
    contenga instrucciones o datos no autorizados).
    Mitigaciones ya implementadas:
      - response_format: json_schema (strict=true) en ambas llamadas: el
        campo "clasificacion" esta restringido por enum a 4 valores
        posibles; el LLM no puede "declarar" una categoria arbitraria ni
        anexar texto libre fuera del esquema (ver Anexo B).
      - El mensaje del lead se inyecta exclusivamente como dato en el rol
        "user" con una etiqueta explicita ("Mensaje: "), nunca en el rol
        "system", limitando (sin eliminar del todo) la superficie de
        confusion de roles.
      - Ningun campo de salida de la IA se ejecuta ni se interpreta como
        comando: ia_clasificacion, ia_prioridad, ia_resumen e ia_respuesta
        se persisten como datos y se muestran como texto/HTML sanitizado
        en el dashboard (ver LLM02).
    Evidencia empirica (corrida real, no simulada, sobre CP-11):
    ver subseccion 5.1.

  [LLM02] Insecure Output Handling
    Riesgo: el email generado (ia_respuesta) es HTML producido por el LLM
    y se envia directamente por Gmail; si un atacante lograra inyectar
    HTML/JS malicioso en ese campo, podria intentar phishing con la
    identidad de la empresa.
    Mitigacion: el prompt exige HTML "valido, diseno profesional y
    responsive" pero el canal de salida es un cliente de correo (Gmail),
    no un navegador que ejecute <script> en el contexto de la aplicacion
    propia — el vector de XSS clasico (robo de sesion/cookies del
    dashboard) no aplica a este campo porque el dashboard trunca el
    mensaje ORIGINAL del lead a 120 caracteres como texto plano (ver
    Anexo I) y no renderiza ia_respuesta como HTML embebido sin sanitizar.
    Pendiente: no hay sanitizacion explicita (bleach/DOMPurify) del HTML
    generado antes de enviarlo; si en el futuro ia_respuesta se muestra en
    el dashboard, debe sanitizarse. Estado: PARCIALMENTE CUBIERTO.

  [LLM06] Sensitive Information Disclosure
    Riesgo: el prompt de clasificacion envia nombre, apellido, fuente y
    mensaje del lead a la API de OpenAI (EE.UU.), un tercero. Ya
    documentado en la seccion 3 (transferencia internacional, art. 12,
    Ley 25.326). OpenAI no usa datos de la API para entrenar modelos
    segun sus terminos vigentes.

  [LLM09] Overreliance
    Riesgo: el sistema podria aceptar ciegamente cualquier salida del LLM
    (p. ej. una prioridad manipulada que dispare una notificacion de
    "cliente VIP" falsa al equipo de ventas).
    Mitigacion: fallback centinela 'sin_clasificar' + ia_fallback=true
    ante JSON no parseable, y prioridad=0 forzada por codigo (no por el
    LLM) para todo lead spam (ver M-15/CF-04). El scoring de prioridad
    sigue siendo una señal para el equipo humano, no una decision
    automatica (no dispara acciones irreversibles por si solo).

    Interpretacion: en esta corrida, la combinacion de (a) response_format

    mitigaciones vigentes resistieron estos vectores especificos, no una

    ampliarla si el prompt de sistema cambia.

6. CONCLUSIÓN
------------------------------------------------------------
  El sistema implementa 13 controles de seguridad a nivel de aplicación,
  11 políticas RLS en base de datos, medidas de protección de datos
  (hashing, anonimización de IP, logging sin PII) y mitigaciones
  especificas de LLM (json_schema estricto, confinamiento del input no
  confiable al rol "user", fallback centinela ante fallos de parseo).
  La corrida real sobre CP-11 (seccion 5.1) no encontro casos de prompt
  injection exitoso, aunque la cobertura de esa prueba es acotada (n=3).
  Sin embargo, NO puede afirmarse cumplimiento pleno de la Ley 25.326
  debido a las brechas identificadas en consentimiento e información al
  titular, y LLM02 (sanitizacion de HTML generado) queda parcialmente
  cubierto. Estas brechas son subsanables y constituyen trabajo futuro
  inmediato para un despliegue en producción.
